Прежде всего, спасибо, что нашли время внести свой вклад!

Ниже приведён краткий набор рекомендаций по внесению вклада в Iroha.

Как я могу помочь?
------------------

Перевод документации
~~~~~~~~~~~~~~~~~~~~

Переведённые версии этой документации размещаются рядом с английской
под ``/<language>/``. Сейчас доступны:

* **Турецкий** — `турецкая документация <../tr/>`_ (переведена из
  архивного репозитория :strikelink:`hyperledger-iroha/iroha-docs-l10n
  <https://github.com/hyperledger-iroha/iroha-docs-l10n>`;
  перевод охватывает документацию эпохи Iroha 1.2 и может
  отставать от английской версии)

Планируется поддержка других языков — в том числе польского. Если вы
хотите внести перевод, пожалуйста, свяжитесь с нами через
`Discord <https://discord.com/channels/905194001349627914/905205848547155968>`_.

Сообщение об ошибках
~~~~~~~~~~~~~~~~~~~~

*Ошибка* (bug) — это ошибка, дефект проекта, сбой или неисправность в
Iroha, которая приводит к неверному или неожиданному результату либо к
незапланированному поведению.

Ошибки отслеживаются как `задачи GitHub <https://github.com/hyperledger-iroha/iroha/issues>`_.

Чтобы сообщить об ошибке, `создайте новую задачу <https://github.com/hyperledger-iroha/iroha/issues/new>`_ и
включите в шаблон задачи эти сведения: краткое описание проблемы,
шаги для воспроизведения и любые относящиеся к делу логи. Пожалуйста,
также укажите данные о своей среде (ОС, характеристики устройства,
версия Iroha и т. д.).

Сообщение об уязвимостях
~~~~~~~~~~~~~~~~~~~~~~~~

Хотя мы стремимся предотвращать проблемы безопасности, мы не
предполагаем, что они никогда не возникнут.

Стандартная практика — ответственно и конфиденциально сообщить
поставщику (организации Hyperledger) о проблеме безопасности до её
публичного раскрытия, чтобы можно было подготовить исправление и
минимизировать ущерб от уязвимости.

До Первого крупного релиза (1.0) все уязвимости считаются ошибками,
поэтому смело отправляйте их, как описано выше. После Первого
крупного релиза, пожалуйста, используйте `программу вознаграждения за
ошибки <https://hackerone.com/hyperledger>`__, чтобы отправлять
уязвимости и получать вознаграждение.

В любом случае — не стесняйтесь обратиться к любому из действующих
сопровождающих в личных сообщениях Discord или по электронной почте
(см. файл CONTRIBUTORS.md), если хотите обсудить, является ли ваша
находка уязвимостью или ошибкой.

Предложение улучшений
~~~~~~~~~~~~~~~~~~~~~

*Улучшение* — это код или идея, которые делают **существующий** код или
проект быстрее, стабильнее, переносимее, безопаснее или лучше любым
другим способом.

Улучшения отслеживаются как `задачи GitHub <https://github.com/hyperledger-iroha/iroha/issues>`_.

Чтобы отправить новое предложение об улучшении, `создайте новую задачу <https://github.com/hyperledger-iroha/iroha/issues/new>`_ и
опишите идею: что она улучшает и почему она ценна. Если у вас есть
какие-либо предложения по коду, мы будем рады их рассмотреть.

Задание вопросов
~~~~~~~~~~~~~~~~

*Вопрос* — это любое обсуждение, которое обычно не является ни ошибкой,
ни запросом функции или предложением улучшения. Если у вас есть вопрос
вроде «Как сделать X?» — этот раздел для вас.

Пожалуйста, задайте свой вопрос в `вашем любимом мессенджере
<Места, где активен проект_>`__, чтобы участники сообщества могли
вам помочь. Вы также можете помогать другим!

Ваш первый вклад в код
~~~~~~~~~~~~~~~~~~~~~~

Прочитайте наше `Руководство по стилю C++_` и начните с проверки
`доски GitHub <https://github.com/hyperledger-iroha/iroha/projects/1>`__ или задач с
`меткой good-first-issue <https://github.com/hyperledger-iroha/iroha/issues?q=is%3Aissue+is%3Aopen+label%3Agood-first-issue>`_.
Как-то обозначьте, что работаете над этой задачей: свяжитесь с
командой сопровождающих, сообществом или просто назначьте задачу
себе.

Запросы на слияние
~~~~~~~~~~~~~~~~~~

-  Заполните `требуемый шаблон <https://github.com/hyperledger-iroha/iroha/blob/iroha1-main/.github/PULL_REQUEST_TEMPLATE.md>`_

-  Завершайте все файлы переводом строки в конце

-  **Напишите тесты** для нового кода. Покрытие тестами нового кода
   должно быть не менее 70%

-  Каждый запрос на слияние должен быть проверен и получить
   **не менее двух одобрений от команды сопровождающих**. Узнайте,
   кто является текущим сопровождающим, в файле
   `MAINTAINERS.md <https://github.com/hyperledger-iroha/iroha/blob/iroha1-main/MAINTAINERS.md>`_

-  Когда вы закончите работу, убедитесь, что все проверки CI
   проходят — после этого **выполните squash and merge** вашего
   запроса на слияние

-  Соблюдайте `Руководство по стилю C++_`

-  Соблюдайте `Руководство по стилю Git_`

-  **Документируйте новый код** на основе
   `Руководства по стилю документации_`

-  При работе с **запросами на слияние из форков** проверьте
   `это руководство <https://help.github.com/articles/checking-out-pull-requests-locally>`_

Руководства по стилю
--------------------

Руководство по стилю Git
~~~~~~~~~~~~~~~~~~~~~~~~

-  **Подписывайте каждый коммит** с помощью
   `DCO <https://github.com/apps/dco>`_: ``Signed-off-by: $NAME <$EMAIL>``. Это можно сделать автоматически
   с помощью ``git commit -s``
-  **Используйте настоящее время** («Add feature», а не
   «Added feature»).
-  **Используйте повелительное наклонение** («Deploy docker to...»,
   а не «Deploys docker to...»).
-  Пишите содержательное сообщение коммита.
-  Ограничьте первую строку сообщения коммита 50 символами или
   меньше
-  Первая строка сообщения коммита должна содержать краткое
   описание выполненной работы, вторая строка должна быть пустой,
   третья и последующие строки могут содержать список изменений
   коммита
-  При слиянии в целевую ветку: используйте **Squash and merge**

Руководство по стилю C++
~~~~~~~~~~~~~~~~~~~~~~~~~~

-  Используйте файл с
   `настройками <https://github.com/hyperledger-iroha/iroha/blob/iroha1-main/.clang-format>`_
   clang-format. В интернете доступны руководства (например,
   `вики Kratos <https://github.com/KratosMultiphysics/Kratos/wiki/How-to-configure-clang%E2%80%90format>`_)
-  Соблюдайте
   `CppCoreGuidelines <http://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines>`_
   и `лучшие практики
   C++ <https://lefticus.gitbooks.io/cpp-best-practices>`_.
-  Избегайте
   `зависимого от платформы <https://stackoverflow.com/questions/1558194/learning-and-cross-platform-development-c>`_
   кода.
-  Используйте `C++23 <https://en.wikipedia.org/wiki/C%2B%2B23>`_.
-  Используйте `camelCase <https://en.wikipedia.org/wiki/Camel_case>`_ для
   имён классов и методов, используйте
   `snake\_case <https://en.wikipedia.org/wiki/Snake_case>`_ для
   переменных.

Руководство по стилю документации
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

-  Используйте
   `Doxygen <http://www.doxygen.nl/>`_.
-  Документируйте все публичные API: методы, функции, члены,
   шаблоны, классы...
