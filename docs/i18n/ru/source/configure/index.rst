Параметры, зависящие от развёртывания
=====================================

- ``block_store_path`` (необязательный) задаёт путь к папке, в которой хранятся блоки. Если этот параметр не указан, блоки будут храниться в базе данных.
- ``torii_port`` задаёт порт для внешних коммуникаций. Именно сюда отправляются
  запросы и транзакции.
- ``internal_port`` задаёт порт для внутренних коммуникаций: сервис упорядочивания
  (ordering service), консенсус и загрузчик блоков.
- ``database`` (необязательный) используется для настройки конфигурации базы данных (см. ниже)
- ``pg_opt`` (необязательный) — **устаревший** способ указания учётных данных PostgreSQL:
  hostname, port, username, password и имя базы данных.
  Все данные, кроме имени базы данных, обязательны.
  Если имя базы данных не указано, используется значение по умолчанию — ``iroha_default``.
- ``log`` — необязательный параметр, управляющий уровнем детализации и форматом
  вывода в лог (см. ниже).
- ``utility_service`` (необязательный) — конечная точка для сервисных задач.
  Если присутствует, должна включать адрес ``ip`` и ``port`` для привязки.
  Пример использования служебной конечной точки см. в `документации shepherd <../maintenance/shepherd.html>`_.
- ``metrics`` (необязательный) — конечная точка для мониторинга метрик Iroha. HTTP-сервер Prometheus слушает на этой конечной точке.
  Если присутствует, должна соответствовать формату "[addr]:<port>" и может быть, например, "127.0.0.1:8080", "9090" или ":1234".
  Неверные значения неявно отключают сервер метрик Prometheus. Есть также параметры командной строки ``--metrics_port`` и
  ``--metrics_addr``, позволяющие переопределить этот параметр.
- ``healthcheck_port`` (необязательный) — конечная точка для проверки состояния Iroha. Запрос к этой конечной точке в виде ``http://<host>:<healthcheck_port>/healthcheck`` вернёт информацию о состоянии узла: текущее потребление памяти (``memory_consumption``), текущее количество блоков (``last_block_round``), текущее количество «пустых» раундов (``last_reject_round``), синхронизирует ли узел в данный момент информацию с удалённым узлом (``is_syncing``), находится ли узел сейчас в рабочем состоянии (``status``). 

Также есть необязательный параметр ``torii_tls_params``, который можно включить
в конфигурацию для поддержки TLS при коммуникации с клиентами.

В нём ``port`` — это TCP-порт, к которому будет привязан TLS-сервер, а
``key_pair_path`` — путь к ключу в таком формате, что добавление
``.crt`` к нему даст путь к сертификату в кодировке PEM, а добавление
``.key`` — путь к закрытому ключу в кодировке PEM для этого сертификата
(например, если ``key_pair_path`` равен ``"/path/to/the/keypair"``, iroha будет искать
сертификат по адресу ``"/path/to/the/keypair.crt"``, а ключ — по адресу
``"/path/to/the/keypair.key"``)

.. warning::
   Поле конфигурации ``pg_opt`` устарело, пожалуйста, используйте раздел ``database``!

   Раздел ``database`` переопределяет ``pg_opt``, когда оба указаны в конфигурации.

   И поля ``pg_opt``, и ``database`` необязательны, но должен быть указан хотя бы один из них.

Поля раздела ``database``:

- ``host`` — хост для подключения к PostgreSQL
- ``port`` — порт для подключения к PostgreSQL
- ``user`` — пользователь для подключения к PostgreSQL
- ``password`` — пароль для подключения к PostgreSQL
- ``working database`` — имя базы данных, которая будет использоваться для хранения представления мирового состояния и, по желанию, блоков.
- ``maintenance database`` — имя базы данных, которая будет использоваться для обслуживания рабочей базы данных.
  Например, когда iroha нужно создать или удалить свою рабочую базу данных, она должна подключиться к PostgreSQL через другую базу данных.

Параметры, зависящие от окружения
=================================

- ``max_proposal_size`` \* — максимальное количество транзакций, которое может входить
  в одно предложение (proposal), а значит, и в один блок. Таким образом, изменяя это
  значение, вы определяете размер потенциального блока. Для начала можно оставить
  ``10``. Однако мы рекомендуем увеличивать это число, если у вас много
  транзакций в секунду.

    **Этот параметр влияет на производительность.** Увеличьте его, если в вашей сети проходит большое количество транзакций. Если вы увеличиваете ``max_proposal_size`` из-за выросшей пропускной способности, вы можете увеличивать его независимо. Увеличение этого параметра может улучшить производительность, но обратите внимание, что при достижении определённого значения дальнейшее увеличение может привести к деградации производительности.

- ``vote_delay`` \* — время ожидания в миллисекундах перед отправкой голоса
  следующему узлу. Оптимальное значение сильно зависит от количества узлов Iroha в
  сети (чем больше узлов, тем больше нужен ``vote_delay``). ** Мы настоятельно рекомендуем
  установить его как минимум в одну секунду — иначе, когда часть узлов оказывается труднодоступной, цепочка блоков будет расти очень медленно или даже перестанет расти.**

    **Этот параметр влияет только на механизм консенсуса.** Если ваша сеть быстрая — всё хорошо, и этот параметр почти не влияет на неё. Но если сеть работает медленно, увеличьте его, чтобы дать узлам больше времени на ответ.

- ``mst_enable`` включает или отключает сетевую транспортировку
  мультиподписанных транзакций (MST) в Iroha.
  Обратите внимание, что движок MST работает для любого узла даже при значении флага
  ``false``.
  Флаг лишь разрешает обмениваться информацией о MST-транзакциях между
  узлами.

- ``mst_expiration_time`` — необязательный параметр, задающий период времени
  в минутах, по истечении которого неполностью подписанная транзакция (или пакет транзакций)
  считается истёкшей.
  Значение по умолчанию — 1440.

- ``proposal_creation_timeout`` (ранее назывался ``max_rounds_delay``)\* — необязательный параметр, задающий максимальное время (в миллисекундах), которое сервис упорядочивания ждёт, собирая предложение — то есть собирая транзакции до ``max_proposal_size`` — перед тем как ответить на запрос предложения.
  Значение по умолчанию — 3000.
  Второй, производный тайм-аут — сетевой дедлайн для RPC ``RequestProposal`` между узлами — вычисляется автоматически как ``2 × proposal_creation_timeout`` и не настраивается отдельно.

    **Этот параметр влияет на потребление ресурсов.** Если вы ожидаете, что Iroha будет простаивать длительное время, и хотите сэкономить ресурсы, увеличьте это значение — Iroha будет реже проверять новые транзакции. NB: первая транзакция после периода простоя может быть немного задержана из-за этого. Второй и последующие блоки будут обрабатываться быстрее.

- ``stale_stream_max_rounds`` — необязательный параметр, задающий максимальное
  количество раундов, в течение которых поддерживается открытый статусный поток, пока не поступает обновление статуса.
  Значение по умолчанию — 2.
  Увеличение этого значения сокращает количество повторных подключений клиента для
  отслеживания транзакции, если по какой-то причине она не обновляется новыми раундами.
  Однако большие значения увеличивают среднее число подключённых клиентов в
  каждом раунде.

    Рекомендуется ограничивать этот параметр, чтобы убедиться, что узел не перегружен потоками.

- ``initial_peers`` — необязательный параметр, задающий список узлов, которые узел
  будет использовать после запуска вместо узлов из генезис-блока.
  Это может быть полезно при добавлении в сеть нового узла, если большинство
  начальных узлов могут оказаться вредоносными.
  Список узлов должен быть указан в виде JSON-массива:

.. code-block:: javascript

  "initial_peers": [
    {
      "address": "127.0.0.1:10001",
      "public_key": "bddd58404d1315e0eb27902c5d7c8eb0602c16238f005773df406bc191308929"
    }
  ]

- ``max_past_created_hours``: необязательный параметр, задающий, насколько в прошлом от текущего времени (измеренного на узле) может быть установлено поле `created_time` транзакции. Значение по умолчанию — ``"24"`` часа. Это значение должно совпадать на всех узлах, иначе это может незаметно привести к остановке производства блоков в сети.

Пример из хорошей практики
--------------------------

При равномерном распределении мы получили довольно хорошие результаты — 300 тыс. транзакций за 5 минут.
Транзакции (commit) занимали от 2 секунд до 2 минут.
**Обратите внимание, что результаты всегда зависят от количества узлов в вашей сети, её скорости и параметров хостов, на которых работают узлы.**

Вот конфигурация, которую мы использовали:

.. code-block:: javascript

  "max_proposal_size" : 10000,
  "vote_delay" : 1000,
  "mst_enable" : true,
  "mst_expiration_time": 1440,
  "proposal_creation_timeout": 500,
  "stale_stream_max_rounds": 100000


Переменные окружения
====================

Ещё один способ настроить Iroha — использовать переменные окружения.
Конфигурационный файл и переменные окружения можно комбинировать.
**Параметры, указанные в конфигурационном файле, если они присутствуют, имеют приоритет над заданными через окружение.**

Вот несколько примеров того, как параметры будут выглядеть в

Unix
----

.. code-block:: bash

  export IROHA_BLOCK_STORE_PATH=/tmp/block_store/
  export IROHA_TORII_PORT=50051
  export IROHA_INTERNAL_PORT=10001
  export IROHA_PG_OPT="host=172.19.0.2 port=5432 user=iroha password=helloworld"
  export IROHA_MAX_PROPOSAL_SIZE=10
  export IROHA_VOTE_DELAY=5000
  export IROHA_MST_ENABLE=false
  export IROHA_MST_EXPIRATION_TIME=1440
  export IROHA_PROPOSAL_CREATION_TIMEOUT=3000
  export IROHA_CRYPTO_PROVIDERS_0_KEY=p1
  export IROHA_CRYPTO_PROVIDERS_0_CRYPTO_TYPE=ed25519_sha3_256
  export IROHA_CRYPTO_PROVIDERS_0_PRIVATE_KEY=cc5013e43918bd0e5c4d800416c88bed77892ff077929162bb03ead40a745e88
  export IROHA_CRYPTO_PROVIDERS_0_TYPE=default
  export IROHA_CRYPTO_SIGNER=p1

Windows
-------

.. code-block:: bat

  setx IROHA_BLOCK_STORE_PATH C:\block_store
  setx IROHA_TORII_PORT 50051
  setx IROHA_INTERNAL_PORT 10001

PowerShell
----------

.. code-block:: bash

  $Env:IROHA_BLOCK_STORE_PATH="C:\block_store"
  $Env:IROHA_TORII_PORT="50051"
  $Env:IROHA_INTERNAL_PORT="10001"

Имена параметров
----------------

Как видно, имена параметров не совпадают с теми, что используются в конфигурационном файле.

Они формируются из структуры конфигурации: в начало добавляется фиксированный префикс IROHA, всё переводится в верхний регистр и соединяется с помощью _.
Давайте чуть подробнее посмотрим, как они устроены:

**С простыми строковыми значениями**

В конфигурационном файле:

.. code-block:: javascript

  "block_store_path": "/tmp/block_store/"

В переменных окружения:

.. code-block:: bash

  IROHA_BLOCK_STORE_PATH=/tmp/block_store/


**С массивами**

Массивы индексируются, начиная с 0, и должны идти в прямом порядке без пропуска номеров:

В конфигурационном файле:

.. code-block:: javascript

  "initial_peers": [
    {
      "address": "127.0.0.1:10001",
      "public_key": "bddd58404d1315e0eb27902c5d7c8eb0602c16238f005773df406bc191308929"
    },
    {
      "address": "127.0.0.1:10002",
      "public_key": "bddd58404d1315e0eb27902c5d7c8eb0602c16238f005773df406bc191308920"
    }
  ]

В переменных окружения:

.. code-block:: bash

  IROHA_INITIAL_PEERS_0_ADDRESS=127.0.0.1:10001
  IROHA_INITIAL_PEERS_0_PUBLIC_KEY=bddd58404d1315e0eb27902c5d7c8eb0602c16238f005773df406bc191308929
  IROHA_INITIAL_PEERS_1_ADDRESS=127.0.0.1:10002
  IROHA_INITIAL_PEERS_1_PUBLIC_KEY=bddd58404d1315e0eb27902c5d7c8eb0602c16238f005773df406bc191308920

**Словари с пользовательскими ключами**

Ключи словарей, заданные пользователем, устроены немного сложнее: ключ и значение задаются в отдельных переменных.
Их можно проиллюстрировать на примере настройки криптографических провайдеров:

Криптографические провайдеры
============================

В настоящее время HL Iroha поддерживает один тип провайдеров под названием ``default`` — он включает встроенные криптопровайдеры, такие как криптографическая библиотека HL Iroha (с криптотипом ``ed25519_sha3_256``) и библиотека HL Ursa, в которой Iroha в настоящее время поддерживает криптотип ``ed25519_sha2_256``.

Обе они принимают в качестве параметров только ``crypto_type`` и ``private_key``.

.. note::  Мы работаем над добавлением других типов, включая ``hsm`` — для аппаратных модулей безопасности. Они будут иметь другой набор параметров, который будет добавлен сюда после релиза.

Настройка криптографических провайдеров
---------------------------------------

Чтобы настроить доступные в настоящее время криптопровайдеры, нужно определить провайдеры, которые могут использоваться на узле (см. ``p1`` и ``p2``), а затем выбрать ``signer``, который будет использоваться для подписи сообщений на этом узле:

В конфигурационном файле:

.. code-block:: javascript

  "crypto": {
    "providers": {
      "p1": {
        "crypto_type": "ed25519_sha3_256",
        "private_key": "cc5013e43918bd0e5c4d800416c88bed77892ff077929162bb03ead40a745e88",
        "type": "default"
      },
      "p2": {
        "crypto_type": "ed25519_sha2_256",
        "private_key": "7bab70e95cb585ea052c3aeb27de0afa9897ba5746276aa1c25310383216ceb860eb82baacbc940e710a40f21f962a3651013b90c23ece31606752f298c38d90",
        "type": "default"
      }
    },
    "signer": "p1"
  }

В переменных окружения:

.. code-block:: bash

  IROHA_CRYPTO_PROVIDERS_0_KEY=p1
  IROHA_CRYPTO_PROVIDERS_0_CRYPTO_TYPE=ed25519_sha3_256
  IROHA_CRYPTO_PROVIDERS_0_PRIVATE_KEY=cc5013e43918bd0e5c4d800416c88bed77892ff077929162bb03ead40a745e88
  IROHA_CRYPTO_PROVIDERS_0_TYPE=default
  IROHA_CRYPTO_PROVIDERS_1_KEY=p2
  IROHA_CRYPTO_PROVIDERS_1_CRYPTO_TYPE=ed25519_sha2_256
  IROHA_CRYPTO_PROVIDERS_1_PRIVATE_KEY=7bab70e95cb585ea052c3aeb27de0afa9897ba5746276aa1c25310383216ceb860eb82baacbc940e710a40f21f962a3651013b90c23ece31606752f298c38d90
  IROHA_CRYPTO_PROVIDERS_1_TYPE=default
  IROHA_CRYPTO_SIGNER=p1


Логирование
===========

В Iroha логирование можно настроить настолько детально, насколько нужно.
Каждый компонент имеет собственную конфигурацию логирования со свойствами, наследуемыми от
своего родителя, которые можно переопределить через конфигурационный файл.
Это означает, что все логгеры компонентов организованы в дерево с единственным корнем.
Соответствующий раздел конфигурационного файла содержит переопределяемые значения:

В конфигурационном файле:

.. code-block:: javascript

  "log": {
    "level": "trace",
    "patterns": {
      "debug": "don't panic, it's %v.",
      "error": "MAMA MIA! %v!"
    },
    "children": {
      "KeysManager": {
        "level": "trace"
      },
      "Irohad": {
        "children": {
          "Storage": {
            "level": "trace",
            "patterns": {
              "debug": "thread %t: %v."
            }
          }
        }
      }
    }
  }

В переменных окружения:

.. code-block:: bash

  IROHA_LOG_LEVEL=trace
  IROHA_LOG_PATTERNS_0_KEY=debug
  IROHA_LOG_PATTERNS_0="don't panic, it's %v."
  IROHA_LOG_PATTERNS_1_KEY=error
  IROHA_LOG_PATTERNS_1="MAMA MIA! %v!"
  IROHA_LOG_CHILDREN_0_KEY=KeysManager
  IROHA_LOG_CHILDREN_0_LEVEL=trace
  IROHA_LOG_CHILDREN_1_KEY=Irohad
  IROHA_LOG_CHILDREN_1_CHILDREN_0_KEY=Storage
  IROHA_LOG_CHILDREN_1_CHILDREN_0_LEVEL=trace
  IROHA_LOG_CHILDREN_1_CHILDREN_0_PATTERNS_0_KEY=debug
  IROHA_LOG_CHILDREN_1_CHILDREN_0_PATTERNS_0="thread %t: %v."

Каждая часть этого раздела конфигурации необязательна.

- ``level`` задаёт уровень детализации.
  Доступные значения (в порядке убывания детализации):

  - ``trace`` — печатать всё
  - ``debug``
  - ``info``
  - ``warning``
  - ``error``
  - ``critical`` — печатать только критические сообщения

- ``patterns`` управляет форматированием каждой строки лога для разных
  уровней детализации.
  Каждое значение также переопределяет менее детальные уровни.
  Так что в примере выше шаблон "don't panic" также применяется к уровням info и
  warning, а шаблон уровня trace — единственный, который не
  инициализирован в конфигурации (он будет установлен в значение по умолчанию, заданное в коде).

.. note::  Даже если для одного компонента указано несколько шаблонов, этот компонент будет использовать только один шаблон — тот, что соответствует выбранному уровню логирования. Однако шаблоны будут унаследованы и могут использоваться в дочерних логгерах.

- ``children`` описывает переопределения дочерних узлов.
  Ключи — это имена компонентов, а значения имеют тот же синтаксис
  и семантику, что и корневая конфигурация логирования.
