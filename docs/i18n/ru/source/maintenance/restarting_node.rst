Перезапуск узла Iroha с существующим WSV
=========================================

Раньше, в случаях когда нужно было обновить узел или он по какой-то
причине выключался, был только один вариант — перечитать все блоки,
чтобы воссоздать согласованный `world state view (также называемый
WSV) <../concepts_architecture/architecture.html#world-state-view>`__.
Чтобы запустить узел быстрее, теперь возможно повторно использовать
существующую базу WSV после быстрой проверки. Для этого ``hash``
верхнего блока и ``height`` blockstorage включены в WSV.

.. warning::
	На администраторах узла лежит обязанность убедиться, что WSV
	не редактируется вручную – только Irohой или
	`скриптом миграции <#changing-iroha-version-migration>`__.
	Ручное редактирование или редактирование скрипта миграции не
	по надёжным рекомендациям может привести к несогласованной
	сети. Делайте это на свой страх и риск (мы вас
	предупредили).

Хотя это может быть отличной идеей для некоторых случаев,
учтите, что есть определённые особенности повторного использования
WSV по сравнению с его восстановлением из blockstorage:

| :red:`Точка доверия`
| **Повторное использование WSV:** мы должны полагаться и на
  blockstorage, и на WSV.
| **Восстановление WSV из block storage:** мы доверяем только
  genesis block.


| :red:`Целостность`
| **Повторное использование WSV:** blockstorage и WSV должны
  соответствовать друг другу! Iroha не будет это проверять.
| **Восстановление WSV из block storage:** Iroha проверит каждый
  блок при восстановлении WSV.
	Любая ошибка в blockstorage будет найдена (конечно, кроме
	genesis block).
	WSV гарантированно соответствует blockstorage.

| :red:`Время`
| **Повторное использование WSV:** Iroha почти сразу готова
  работать в сети.
| **Восстановление WSV из block storage:** чем больше
  blockstorage — тем дольше занимает его восстановление и начало
  работы.

.. note:: Если локальный ledger, который выключился, имеет
больше блоков, чем должен, и правильный WSV среди них — это
нормально, Iroha возьмёт WSV правильного блока.
	Если блоков меньше, чем должно — вариант повторного
	использования WSV вам не подойдёт.
	Пожалуйста, восстановите его из блоков.


Отбрасывание WSV
^^^^^^^^^^^^^^^^

По умолчанию Iroha повторно использует состояние WSV при запуске,
поэтому флаг `--reuse_state` больше не нужен. Однако он оставлен
для обратной совместимости. Если вы хотите отбросить состояние
WSV, запустите Irohу с флагом ``--drop_state``. С этим флагом
Iroha сбросит и перезапишет базу состояния.

Версия схемы базы состояния
^^^^^^^^^^^^^^^^^^^^^^^^^^

При повторном использовании существующего WSV Iroha выполняет
проверку совместимости версии схемы. Она не запустится и не будет
изменять базу каким-либо образом, если её схема не совместима с
используемой Irohой.

Если ваша схема была создана Irohой версии v1.1.1 или ниже, скорее
всего она не включает информацию о версии. В этом случае нужно
добавить её вручную. Рекомендуем использовать наш скрипт для этой
цели — он находится `здесь
<https://github.com/hyperledger-iroha-state-migration-tool/blob/master/state_migration.py>`__.
Чтобы принудительно (т.е. без какого-либо `процесса миграции
<#changing-iroha-version-migration>`__) установить версию схемы,
запустите скрипт с флагом `--force_schema_version` и передайте
версию бинарника Iroha, который использовался для создания вашей
схемы.

.. warning::
  Прежде чем принудительно записывать номера версий схемы,
  дважды проверьте версию irohad, создавшую схему.
  Никакие проверки не выполняются при принудительной установке
  номеров схемы, поэтому легко сломать базу состояния в будущем
  (во время следующей миграции).

Изменение версии Iroha. Миграция.
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
Если вы хотите изменить версию Iroha, сохранив WSV, рекомендуется
выполнить миграцию. Хотя она может быть ненужной (Iroha откажется
запускаться, если схема несовместима), в общем случае мы
улучшаем схему с каждой версией, и миграция может быть хорошей
идеей для лучшей производительности. Рекомендуется выполнить
резервное копирование базы перед миграцией, используя стандартные
`рекомендации PostgreSQL
<https://www.postgresql.org/docs/current/backup.html>`__.

Для выполнения миграции используйте наш `скрипт
<https://github.com/hyperledger-iroha-state-migration-tool/blob/master/state_migration.py>`__.

Он загрузит информацию о схеме из базы и сопоставит её с шагами
миграции (по умолчанию сценарии миграции определены в каталоге
``migration_data`` в той же папке, что и скрипт). Затем он найдёт
все пути миграции, которые переведут вашу базу в нужную версию, и
попросит вас выбрать один.

.. seealso::
	`Здесь
	<https://github.com/hyperledger-iroha-state-migration-tool/blob/master/README.md>`__
	есть подробности о различных случаях миграции и примеры,
	которые можно проверить для выполнения миграции

Режим синхронизации WSV.
^^^^^^^^^^^^^^^^^^^^^^^

Укажите опции ``--wait_for_new_blocks`` для режима синхронизации
WSV. Iroha восстанавливает WSV из blockstore и ждёт добавления
новых блоков извне. В этом режиме Iroha не будет выполнять
сетевые операции.
