Запросы
=======

Запрос — это обращение к определённой части World State View — текущего состояния блокчейна.
Запрос не может изменять содержимое цепочки, а ответ возвращается
любому клиенту сразу после того, как принявший пир обработал запрос.

Валидация
^^^^^^^^^^

Валидация для всех запросов включает:

- метку времени — не должна быть из прошлого (настраивается в `конфигурации Iroha <../../configure/index.html#environment-specific-parameters>`_) или из будущего (диапазон в 5 минут относительно времени пира)
- подпись создателя запроса — используется для проверки личности создателя запроса
- счётчик запроса — проверяется, что он инкрементируется с каждым последующим запросом от создателя запроса
- роли — в зависимости от роли создателя запроса: диапазон состояния, доступный для запроса, может относиться к тому же аккаунту, аккаунту в домене, ко всей цепочке или не быть разрешён вовсе

Пагинация результатов
^^^^^^^^^^^^^^^^^^^^^^

Некоторые запросы поддерживают `TxPaginationMeta`, который позволяет настраивать и сортировать результат запроса различными способами, что может быть использовано при разработке.
Пагинация работает вместе с параметрами упорядочивания, подобно `ORDER BY в языке SQL <https://www.postgresql.org/docs/12/sql-select.html#SQL-ORDERBY>`_ – "строки результата сортируются в соответствии с указанным выражением (в Iroha — полем). Если две строки равны согласно левому выражению, они сравниваются согласно следующему выражению и так далее."

Вот как указывается "выражение":

.. code-block:: proto

    enum Field {
        kCreatedTime = 0;
        kPosition = 1;
    }

Существуют 2 основы упорядочивания — по времени создания и в зависимости от номера блока.

Для каждого Field существуют направления по возрастанию и по убыванию:

.. code-block:: proto

    enum Direction {
        kAscending = 0;
        kDescending = 1;
    }

Теперь само упорядочивание:

.. code-block:: proto

    message Ordering {
        message FieldOrdering {
          Field field = 1;
          Direction direction = 2;
        }
        repeated FieldOrdering sequence = 1;
    }

После того как упорядочивание задано, можно выполнить пагинацию:

.. literalinclude:: ../../../../shared_model/schema/queries.proto
    :language: proto
    :start-at: message TxPaginationMeta {
    :end-before: message AssetPaginationMeta {

Получение ожидающих транзакций
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

Назначение
----------

GetPendingTransactions используется для получения списка ожидающих (не полностью подписанных) `мультиподписных транзакций <../../concepts_architecture/glossary.html#multisignature-transactions>`_
или `пакетов транзакций <../../concepts_architecture/glossary.html#batch-of-transactions>`__, выпущенных аккаунтом создателя запроса.

.. note:: Этот запрос использует `пагинацию <#result-pagination>`_ для более быстрых и удобных ответов на запрос. Пожалуйста, прочитайте о ней и укажите пагинацию перед отправкой запроса, а также `структуру запроса <#what-is-added-to-the-request-structure-in-case-of-pagination>`_.

Схема запроса
-------------

.. code-block:: proto

    message GetPendingTransactions {
        TxPaginationMeta pagination_meta = 1;
    }

Все полу-подписанные мультиподписные (ожидающие) транзакции пользователя могут быть запрошены.
Максимальное количество транзакций в ответе может быть ограничено полем **page_size**.
Все ожидающие транзакции хранятся до тех пор, пока не соберут достаточно подписей или не истекут.
Взаимный порядок ожидающих транзакций или пакетов транзакций сохраняется для пользователя.
Это позволяет пользователю запрашивать все транзакции последовательно — страница за страницей.
Каждый ответ может содержать ссылку на следующий пакет или транзакцию, которую можно запросить.
Размер страницы может быть больше размера следующего пакета (в транзакциях).
В этом случае будет возвращено несколько пакетов или транзакций.
Во время навигации по страницам следующий пакет может собрать недостающие подписи до того, как будет запрошен.
Это приведёт к ответу на запрос с ошибкой состояния из-за отсутствующего хэша пакета.

Пример
------

Если есть два ожидающих пакета по три транзакции каждый, а пользователь запрашивает ожидающие транзакции
с размером страницы 5, то транзакции первого пакета будут в ответе, а ссылка
(хэш первой транзакции и размер пакета, даже если фактически это одна транзакция) на второй пакет
также будет указана.
Транзакции второго пакета не включены в первый ответ, потому что пакет не может быть разделён
на несколько частей, и в ответе могут содержаться только полные пакеты.

            string first_tx_hash = 1;
            uint32 batch_size = 2;
        }
        repeated Transaction transactions = 1;
        uint32 all_transactions_size = 2;
        BatchInfo next_batch_info = 3;
    }

Получение деталей аккаунта
^^^^^^^^^^^^^^^^^^^^^^^^^^^

Назначение
----------

Для получения деталей аккаунта можно использовать запрос `GetAccountDetail`. Детали аккаунта — это пары ключ-значение, разделённые на категории по авторам (writers). Авторы — это аккаунты, которые добавили соответствующую деталь аккаунта. Пример такой структуры:

.. code-block:: json

    {
        "account@a_domain": {
            "age": 18,
            "hobbies": "crypto"
        },
        "account@b_domain": {
            "age": 20,
            "sports": "basketball"
        }
    }

Здесь можно увидеть четыре детали аккаунта — "age", "hobbies" и "sports" — добавленные двумя авторами — "account@a_domain" и "account@b_domain". Все эти детали, очевидно, относятся к одному и тому же аккаунту.

Схема запроса
-------------

.. code-block:: proto

    message AccountDetailRecordId {
        string writer = 1;
        string key = 2;
    }

    message AccountDetailPaginationMeta {
        uint32 page_size = 1;
        AccountDetailRecordId first_record_id = 2;
    }

    message GetAccountDetail {
        oneof opt_account_id {
          string account_id = 1;
        }
        oneof opt_key {
          string key = 2;
        }
        oneof opt_writer {
          string writer = 3;
        }
        AccountDetailPaginationMeta pagination_meta = 4;
    }

.. note::
    Обратите внимание, что все поля, кроме метаданных пагинации, являются необязательными.
    Причины этого описаны ниже.

.. warning::
    Метаданные пагинации могут отсутствовать в запросе по причинам совместимости, но такое поведение устарело и его следует избегать.

Примеры использования
---------------------

Снова рассмотрим пример деталей с начала и посмотрим, как разные варианты запросов `GetAccountDetail` изменят итоговый ответ.

.. code-block:: json

    {
        "account@a_domain": {
            "age": 18,
            "hobbies": "crypto"
        },
        "account@b_domain": {
            "age": 20,
            "sports": "basketball"
        }
    }

**account_id не задан**

Если account_id не задан — остальные поля могут быть пустыми или нет — он автоматически будет заменён аккаунтом создателя запроса, что приведёт к одному из следующих случаев.

**задан только account_id**

В этом случае будут возвращены все детали об этом аккаунте, что приведёт к следующему ответу:

.. code-block:: json

    {
        "account@a_domain": {
            "age": 18,
            "hobbies": "crypto"
        },
        "account@b_domain": {
            "age": 20,
            "sports": "basketball"
        }
    }

**заданы account_id и key**

Здесь будут возвращены детали, добавленные всеми авторами под указанным ключом. Например, если мы запросили ключ "age", мы получим такой ответ:

.. code-block:: json

    {
        "account@a_domain": {
            "age": 18
        },
        "account@b_domain": {
            "age": 20
        }
    }

**заданы account_id и writer**

Теперь ответ будет содержать все детали об этом аккаунте, добавленные одним конкретным автором. Например, если мы запросили автора "account@b_domain", мы получим:

.. code-block:: json

    {
        "account@b_domain": {
            "age": 20,
            "sports": "basketball"
        }
    }

**заданы account_id, key и writer**

Наконец, если заданы все три поля, результат будет содержать детали, добавленные конкретным автором под конкретным ключом. Например, если мы запросили ключ "age" и автора "account@a_domain", мы получим:

.. code-block:: json

    {
        "account@a_domain": {
            "age": 18
        }
    }

Получение коммитов
^^^^^^^^^^^^^^^^^^^

Назначение
----------

Чтобы получать новые блоки сразу после их коммита, пользователь может вызывать RPC-вызов `FetchCommits` к сети Iroha.

Схема запроса
-------------

Аргументы запроса не требуются


Схема ответа
------------

.. code-block:: proto

    message BlockQueryResponse {
        oneof response {
            BlockResponse block_response = 1;
            BlockErrorResponse block_error_response = 2;
        }
    }

    message BlockResponse {
        Block block = 1;
    }

    message BlockErrorResponse {
        string message = 1;
    }

Обратите внимание, что возвращается поток `BlockQueryResponse`.

Структура ответа
----------------

.. csv-table::
    :header: "Поле", "Описание", "Ограничение", "Пример"
    :widths: 15, 30, 20, 15

    "Блок", "блок Iroha", "только закоммиченные блоки", "{ 'block_v1': ....}"

Возможные ошибки проверки состояния
-----------------------------------

.. csv-table::
    :header: "Код", "Название ошибки", "Описание", "Как решить"

    "1", "Не удалось получить поток блоков", "Произошла внутренняя ошибка", "Попробуйте снова или обратитесь к разработчикам"
    "2", "Нет таких разрешений", "У создателя запроса нет ни одного из разрешений на получение блоков", "Предоставьте разрешение `can_get_block <permissions.html#can-get-blocks>`__"
    "3", "Недействительные подписи", "Подписи этого запроса не прошли проверку", "Добавьте больше подписей и убедитесь, что подписи запроса являются подмножеством подписантов аккаунта"

.. note::
    `BlockErrorResponse` содержит только поле `message`.
    В случае ошибки проверки состояния оно будет "stateful invalid".
    `GetBlock <#get-block>`__ требует то же разрешение `can_get_block <permissions.html#can-get-blocks>`__.
    Поэтому его можно использовать с `height = 1` (первый блок всегда присутствует) для проверки недействительных подписантов или недостаточных разрешений.
