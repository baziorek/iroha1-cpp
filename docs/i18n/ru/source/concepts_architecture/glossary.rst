Аккаунт
=======

Сущность Iroha, способная выполнять заданный набор действий.
Каждый аккаунт принадлежит одному из существующих `доменов <Домен_>`__.

У аккаунта есть некоторое количество `ролей <Роль_>`__ (может быть и ноль) — это коллекция разрешений.
Только `отчуждаемые разрешения <Отчуждаемое разрешение_>`__ назначаются аккаунту напрямую.


Актив
=====

Любой счётный товар или ценность.
Каждый актив связан с одним из существующих `доменов <Домен_>`__.
Например, актив может представлять любые подобные единицы — денежную единицу, слиток золота, единицу недвижимости и т.д.

Блок
====

Данные транзакций постоянно записываются в файлы, называемые блоками.
Блоки организованы в линейную последовательность во времени (также известную как цепочка блоков) [#f1]_.

Блоки подписываются криптографическими подписями `пиров <Пир_>`__ Iroha, проголосовавших за этот блок во время `консенсуса <Консенсус_>`__.
Подписываемое содержимое называется полезной нагрузкой (payload), поэтому структура блока выглядит так:

.. image:: ../../image_assets/block.png
    :width: 80%
    :align: center
    :alt: Структура блока Iroha

*Вне полезной нагрузки*

    - signatures — подписи пиров, проголосовавших за блок во время раунда консенсуса

*Внутри полезной нагрузки*

    - height — количество блоков в цепочке до данного блока
    - timestamp — время Unix (в миллисекундах) формирования блока пиром
    - массив транзакций, успешно прошедших валидацию и этап консенсуса
    - хеш предыдущего блока в цепочке
    - хеши отклонённых транзакций — массив хешей транзакций, не прошедших этап stateful-валидации; это поле необязательно


Клиент
======

Любое приложение, использующее Iroha, считается клиентом.

Отличительная особенность Iroha заключается в том, что все клиенты используют простые абстракции клиент-сервер при взаимодействии с сетью пиров: они не используют никаких абстракций, специфичных для блокчейн-систем.
Например, в Bitcoin клиенты должны валидировать блоки, а в Hyperledger Fabric им нужно опрашивать несколько пиров, чтобы убедиться, что транзакция записана в блок, тогда как в Hyperledger Iroha клиент взаимодействует с любым пиром так же, как с единственным сервером.

Команда
=======

Команда — это намерение изменить `состояние <architecture.html#world-state-view>`__ сети.
Например, чтобы создать новую `роль <Роль_>`__ в Iroha, необходимо выполнить команду `Create role <../develop/api/commands.html#create-role>`__.

Консенсус
=========

Алгоритм консенсуса — это процесс в компьютерных науках, используемый для достижения согласия относительно единого значения данных среди распределённых процессов или систем.
Алгоритмы консенсуса разработаны для обеспечения надёжности в сети, включающей множество ненадёжных узлов.
Решение этой задачи — известной как проблема консенсуса — важно в распределённых вычислениях и мультиагентных системах.

*Консенсус как алгоритм*

Алгоритм достижения согласия относительно блока среди пиров в сети. Его наличие в системе повышает надёжность.

О консенсусе как компоненте Iroha см. `эту ссылку <architecture.html#block-consensus-yac>`__; подробное описание протокола YAC см. в `документации YAC <yac.html>`_.

Домен
======

Именованная абстракция для группировки `аккаунтов <Аккаунт_>`__ и `активов <Актив_>`__.
Например, она может представлять организацию в группе организаций, работающих с Iroha.

Пир
===

Узел, являющийся частью сети Iroha.
Он участвует в процессе `консенсуса <Консенсус_>`_.

Пир также может быть зарегистрирован как **syncing peer** — узел, который лишь
следует за реестром (например, для резервного копирования или аудита), не принимая
участия в голосовании консенсуса. Syncing-пиры добавляются обычной
командой `AddPeer <../develop/api/commands.html#add-peer>`__ с записью пира,
помеченной как syncing; применяется то же разрешение ``can_add_peer``.
Они получают состояние консенсуса напрямую, чтобы иметь возможность
догнать сеть, но не предлагают блоки и не голосуют.

Разрешение
==========

Именованное правило, дающее привилегию выполнять команду.
Разрешение **не может** быть выдано `аккаунту <Аккаунт_>`__ напрямую; вместо этого аккаунт имеет роли, которые являются коллекциями разрешений. Хотя есть исключение, см. `Отчуждаемое разрешение <Отчуждаемое разрешение_>`__.

`Список разрешений Iroha <../develop/api/permissions.html>`_.

Отчуждаемое разрешение
----------------------

Только отчуждаемое разрешение выдаётся `аккаунту <Аккаунт_>`__ напрямую.
Аккаунт, владеющий отчуждаемым разрешением, может выполнять некоторое конкретное действие от имени другого аккаунта.
Например, если аккаунт a@domain1 даёт аккаунту b@domain2 разрешение на перевод активов — тогда b@domain2 может переводить активы a@domain1 кому угодно.

Предложение
===========

Набор `транзакций <Транзакция_>`__, прошедших только `stateless-валидацию <Stateless-валидация_>`__.

Проверенное предложение
-----------------------

Набор транзакций, прошедших и `stateless-валидацию <Stateless-валидация_>`__, и `stateful-валидацию <Stateful-валидация_>`__, но ещё не зафиксированных.

Запрос
======

Запрос к Iroha, который **не** изменяет `состояние <architecture.html#world-state-view>`__ сети.
Выполняя запрос, клиент может запрашивать данные из состояния, например баланс своего аккаунта, историю транзакций и т.д.

Кворум
======

В контексте подписания транзакций кворум — это минимальное количество подписей, необходимое, чтобы считать транзакцию подписанной.
Значение по умолчанию — 1.
Для `транзакций MST <Мультиподписные транзакции_>`__ это число нужно увеличить.

Каждый аккаунт может привязать дополнительные публичные ключи и увеличить собственный кворум.

Роль
====

Именованная абстракция, содержащая набор `разрешений <Разрешение_>`__.

Подписант
=========

Представляет сущность, которая может подтверждать мультиподписные транзакции для `аккаунта <Аккаунт_>`__.
Его можно прикрепить к аккаунту через `AddSignatory <../develop/api/commands.html#add-signatory>`__ и открепить через `RemoveSignatory <../develop/api/commands.html#remove-signatory>`__.

Транзакция
==========

Упорядоченный набор `команд <Команда_>`__, который применяется к реестру атомарно.
Любая невалидная команда внутри транзакции приводит к отклонению всей транзакции в процессе валидации.

Структура транзакции
--------------------

**Payload** хранит все поля транзакции, кроме подписей:

    - Время создания (unix time, в миллисекундах)
    - Account ID создателя транзакции (username@domain)
    - Поле кворума (указывает требуемое количество подписей)
    - Повторяющиеся команды, подробно описанные в `разделе команд <../develop/api/commands.html>`__
    - Метаинформация пакета (необязательная часть). Подробности см. в `Пакет транзакций`_


**Подписи** содержат одну или несколько подписей (публичный ключ ed25519 + подпись)

Уменьшенный хеш транзакции
^^^^^^^^^^^^^^^^^^^^^^^^^

Уменьшенный хеш вычисляется по полезной нагрузке транзакции, исключая метаинформацию пакета.
Используется в `Пакет транзакций`_.


Статусы транзакций
------------------

Hyperledger Iroha поддерживает как push-, так и pull-модель взаимодействия с клиентом.
Клиент, использующий pull-модель, запрашивает у пира Iroha обновления статусов транзакций, отправляя хеши транзакций и ожидая ответа.
В отличие от этого, push-взаимодействие выполняется через прослушивание потока событий для каждой транзакции.
В любом из этих режимов набор статусов транзакций одинаков:

    Посмотрите её и дайте нам знать, что вы думаете, в комментариях!

Набор статусов транзакций
^^^^^^^^^^^^^^^^^^^^^^^^^

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - Статус
     - Значение
   * - ``NOT_RECEIVED``
     - Запрошенный пир не имеет этой транзакции.
   * - ``ENOUGH_SIGNATURES_COLLECTED``
     - Мультиподписная транзакция имеет достаточно подписей и будет
       провалидирована.
   * - ``MST_PENDING``
     - Мультиподписной транзакции всё ещё нужно больше подписей, чтобы
       достичь кворума.
   * - ``MST_EXPIRED``
     - Мультиподписная транзакция больше не валидна и будет
       удалена.
   * - ``STATELESS_VALIDATION_FAILED``
     - Транзакция сформирована неверно или подписи невалидны; причина
       возвращается.
   * - ``STATELESS_VALIDATION_SUCCESS``
     - Транзакция прошла stateless-валидацию; возвращается сразу после
       её отправки.
   * - ``STATEFUL_VALIDATION_FAILED``
     - Команда нарушает зависящие от состояния правила (баланс, разрешения,
       и т.д.); причина возвращается.
   * - ``STATEFUL_VALIDATION_SUCCESS``
     - Транзакция прошла stateful-валидацию.
   * - ``COMMITTED``
     - Транзакция является частью блока, получившего достаточно голосов
       и находящегося в хранилище блоков.
   * - ``REJECTED``
     - Транзакция была отклонена во время stateful-валидации на предыдущем
       раунде консенсуса; её хеш хранится в хранилище
       `блоков <Блок_>`__ для предотвращения атак повторного воспроизведения.

Ожидающие транзакции
^^^^^^^^^^^^^^^^^^^^

Любая транзакция, у которой в данный момент меньше подписей, чем `Кворум`_ аккаунта-создателя транзакции, считается ожидающей.
Ожидающая транзакция будет отправлена на `Stateful-валидация`_, как только механизм `мультиподписи <Мультиподписные транзакции_>`__ соберёт требуемое для кворума количество подписей.

Транзакция, уже имеющая кворум подписей, также может считаться ожидающей в случаях,
когда транзакция является частью `Пакет транзакций`_ и в нём есть полностью неподписанная транзакция.

Пакет транзакций
================

Пакет транзакций — это функция, позволяющая отправлять в Iroha несколько транзакций одновременно с сохранением их порядка.

Каждая транзакция внутри пакета содержит метаинформацию пакета.
Метаинформация пакета содержит идентификатор типа пакета (атомарный или упорядоченный) и список `уменьшенных хешей <Уменьшенный хеш транзакции_>`_ всех транзакций внутри пакета.
Порядок хешей определяет последовательность транзакций.

Пакет может содержать транзакции, созданные разными аккаунтами.
Любая транзакция внутри пакета может требовать одну или `несколько <Мультиподписные транзакции_>`__ подписей (зависит от кворума, установленного для аккаунта-создателя транзакции).
Хотя бы одна транзакция внутри пакета должна иметь хотя бы одну подпись, чтобы пакет прошёл `Stateless-валидация`_.

Вы можете прочитать статью о пакетах на нашей странице Contributors на `Medium <https://medium.com/iroha-contributors/batches-in-iroha-117614cf1e88>`__.

Атомарный пакет
--------------

Все транзакции внутри атомарного пакета должны пройти `Stateful-валидация`_, чтобы пакет был применён к реестру.

Когда атомарный пакет не проходит stateful-валидацию, каждая транзакция в пакете получает собственные обновления статуса, поэтому транзакция, вызвавшая сбой, может быть идентифицирована из потока статусов:

- Транзакция, содержащая упавшую команду, получает ``STATEFUL_VALIDATION_FAILED`` с непустым ``err_or_cmd_name`` (имя упавшей команды), специфичным для команды ``error_code`` (значение кодов см. в `разделе команд <../develop/api/commands.html>`__), и ``failed_cmd_index``, равным позиции упавшей команды **внутри этой транзакции** (а не внутри пакета).
- Каждая другая транзакция в пакете получает ``STATEFUL_VALIDATION_FAILED`` с пустым ``err_or_cmd_name``, ``error_code`` ``1`` и ``failed_cmd_index``, равным ``18446744073709551615`` (``SIZE_MAX``, означает «конкретной команды нет»), а затем ``REJECTED``, когда пакет будет зафиксирован в блоке.

Поэтому чтобы узнать, какая транзакция сломала пакет, ищите обновление статуса, у которого ``err_or_cmd_name`` не пуст; ``failed_cmd_index`` тогда укажет, какая команда внутри этой транзакции упала.

Упорядоченный пакет
------------------

Упорядоченный пакет сохраняет только последовательность транзакций, применяемых к реестру.
Все транзакции, способные пройти stateful-валидацию внутри пакета, будут применены к реестру.
Сбой валидации одной транзакции НЕ приведёт напрямую к сбою всего пакета.

Мультиподписные транзакции
==========================

Транзакция, у которой `Кворум`_ больше единицы, считается мультиподписной (также называемой mst).
Чтобы достичь `stateful-валидности <Stateful-валидация_>`__, требуется подтверждение от `подписантов <Подписант_>`__ аккаунта-создателя.
Этим участникам нужно отправить ту же транзакцию со своей подписью.

Валидация
=========

Существует два вида валидации — stateless и stateful.

Stateless-валидация
------------------

Выполняется в `Torii <architecture.html#torii>`__.
Проверяет, что объект корректно сформирован, включая подписи.

Stateful-валидация
------------------

Выполняется в `Проверенное предложение <Проверенное предложение_>`__.
Валидируется относительно `Представление состояния мира <architecture.html#world-state-view>`__.
