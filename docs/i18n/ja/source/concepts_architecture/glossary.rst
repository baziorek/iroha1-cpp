アカウント
==========

指定された一連のアクションを実行できるIrohaのエンティティ。
各アカウントは既存の `ドメイン <ドメイン_>`__ のいずれかに属する。

アカウントはある数の `ロール <ロール_>`__（nullもあり得る）を持ち、これはパーミッションの集まりである。
アカウントに直接割り当てられるのは `付与可能なパーミッション <付与可能なパーミッション_>`__ のみである。


アセット
========

数え上げ可能なあらゆる商品や価値。
各アセットは既存の `ドメイン <ドメイン_>`__ のいずれかに関連付けられる。
例えば、アセットは通貨単位、金の延べ棒、不動産の単位など、あらゆる種類の単位を表現できる。

ブロック
========

トランザクションデータは「ブロック」と呼ばれるファイルに永続的に記録される。
ブロックは時間の経過とともに線形の系列（ブロックチェーンとしても知られる）を構成する [#f1]_。

ブロックは `コンセンサス <コンセンサス_>`__ の過程でこのブロックに投票するIrohaの `ピア <ピア_>`__ の暗号署名で署名される。
署名可能な内容はペイロードと呼ばれるので、ブロックの構造は次のようになる。

.. image:: ../../image_assets/block.png
    :width: 80%
    :align: center
    :alt: Irohaブロック構造

*ペイロードの外*

    - 署名 — コンセンサスのラウンド中にそのブロックに投票したピアの署名

*ペイロードの内*

    - 高さ — チェーン内のブロック数を数えたそのブロックまでの数
    - タイムスタンプ — ピアによるブロック形成のUnix時間（ミリ秒）
    - バリデーションとコンセンサスのステップを正常に通過したトランザクションの配列
    - チェーン内の前のブロックのハッシュ
    - 拒否されたトランザクションのハッシュ — ステートフルバリデーションのステップを通過しなかったトランザクションのハッシュの配列。このフィールドは任意である


クライアント
============

Irohaを使用するあらゆるアプリケーションはクライアントとして扱われる。

Irohaの特徴的な点は、すべてのクライアントがピアネットワークとやり取りする際に単純なクライアント・サーバー抽象化のみを使用し、ブロックチェーン関連システム固有の抽象化を一切使用しないことである。
例えば、Bitcoinではクライアントはブロックをバリデーションしなければならず、HL Fabricではトランザクションがブロックに書き込まれたことを確認するために複数のピアをポーリングする必要があるが、HL Irohaではクライアントは単一のサーバーに対するのと同様に任意のピアとやり取りする。

コマンド
========

コマンドはネットワークの `状態 <architecture.html#world-state-view>`__ を変更する意図である。
例えば、Irohaで新しい `ロール <ロール_>`__ を作成するには、`Create role <../develop/api/commands.html#create-role>`__ コマンドを発行しなければならない。

コンセンサス
============

コンセンサスアルゴリズムは、分散されたプロセスやシステム間で単一のデータ値についての合意を達成するためにコンピューターサイエンスで用いられるプロセスである。
コンセンサスアルゴリズムは、信頼できない複数のノードを含むネットワークにおいて信頼性を達成するよう設計されている。
コンセンサス問題として知られるこの問題の解決は、分散コンピューティングやマルチエージェントシステムにおいて重要である。

*アルゴリズムとしてのコンセンサス*

ネットワーク内のピア間でブロックについての合意を達成するアルゴリズムである。システムにこれを持たせることで、信頼性が向上する。

Irohaのコンポーネントとしてのコンセンサスについては `このリンク <architecture.html#block-consensus-yac>`__ を参照。YACプロトコルの詳細な説明については `YACドキュメント <yac.html>`__ を参照。

ドメイン
========

`アカウント <アカウント_>`__ と `アセット <アセット_>`__ をグループ化するための名前付き抽象化。
例えば、Irohaで取引する組織のグループにおける一つの組織を表現できる。

ピア
====

Irohaネットワークの一部であるノード。
`コンセンサス <コンセンサス_>`_ プロセスに参加する。

ピアは **同期ピア** としても登録できる — コンセンサス投票に参加せずに台帳だけを追従するノード（例えばバックアップや監査目的）。同期ピアは、同期ピアとしてマークされたピアレコードを使って通常の `AddPeer <../develop/api/commands.html#add-peer>`__ コマンドで追加される。同じ ``can_add_peer`` パーミッションが適用される。
同期ピアは遅れを取り戻せるようコンセンサス状態を直接受け取るが、ブロックの提案や投票は行わない。

パーミッション
==============

コマンドを実行する特権を与える名前付きルール。
パーミッションは `アカウント <アカウント_>`__ に直接付与 **できない** 。代わりに、アカウントはパーミッションの集まりであるロールを持つ。ただし例外もあり、`付与可能なパーミッション <付与可能なパーミッション_>`__ を参照。

`Irohaパーミッションの一覧 <../develop/api/permissions.html>`_。

付与可能なパーミッション
------------------------

付与可能なパーミッションのみが `アカウント <アカウント_>`__ に直接与えられる。
付与可能なパーミッションを保持するアカウントは、別のアカウントの代理として特定のアクションを実行できる。
例えば、アカウントa@domain1がアカウントb@domain2にアセットを転送できるパーミッションを与えた場合、b@domain2はa@domain1のアセットを誰にでも転送できる。

提案
====

`ステートレスバリデーション <ステートレスバリデーション_>`__ のみを通過した `トランザクション <トランザクション_>`__ の集合。

検証済み提案
------------

`ステートレス <ステートレスバリデーション_>`__ と `ステートフル <ステートフルバリデーション_>`__ の両方のバリデーションを通過したが、まだコミットされていないトランザクションの集合。

クエリ
======

ネットワークの `状態 <architecture.html#world-state-view>`__ を **変更しない** Irohaへのリクエスト。
クエリを実行することで、クライアントは状態からデータを要求できる。例えば自分のアカウントの残高やトランザクション履歴などである。

クォーラム
==========

トランザクション署名の文脈において、クォーラム数とはトランザクションが署名済みと見なされるために必要な最小の署名数である。
デフォルト値は1である。
`MSTトランザクション <マルチシグネチャトランザクション_>`__ ではこの数を増やす必要がある。

各アカウントは追加の公開鍵をリンクして自分のクォーラム数を増やすことができる。

ロール
======

`パーミッション <パーミッション_>`__ の集合を保持する名前付き抽象化。

署名者
======

アカウントに対するマルチシグネチャトランザクションを確認できるエンティティを表す。
`AddSignatory <../develop/api/commands.html#add-signatory>`__ でアカウントに付け、`RemoveSignatory <../develop/api/commands.html#remove-signatory>`__ で外すことができる。

トランザクション
================

台帳にアトミックに適用される `コマンド <コマンド_>`__ の順序付き集合。
トランザクション内の無効なコマンドが1つでもあると、バリデーションプロセス全体でトランザクション全体が拒否される。

トランザクション構造
--------------------

**ペイロード** は署名以外のすべてのトランザクションフィールドを格納する。

    - 作成時刻（Unix時間、ミリ秒）
    - トランザクション作成者のアカウントID（username@domain）
    - クォーラムフィールド（必要な署名数を示す）
    - 詳細は `コマンドセクション <../develop/api/commands.html>`__ で説明されている繰り返しのコマンド
    - バッチメタ情報（任意部分）。詳細は `トランザクションのバッチ`_ を参照


**署名** は1つ以上の署名（ed25519公開鍵＋署名）を含む。

トランザクションハッシュの縮小版
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

縮小ハッシュはバッチメタ情報を除いたトランザクションペイロードに対して計算される。
`トランザクションのバッチ`_ で使用される。


トランザクションステータス
--------------------------

Hyperledger Irohaはクライアントとのプッシュとプルの両方のインタラクションモードをサポートする。
プルモードを使うクライアントは、トランザクションハッシュを送信し応答を待つことでIrohaピアからトランザクションのステータス更新を要求する。
対照的に、プッシュインタラクションは各トランザクションのイベントストリームを購読して実行される。
これらのモードのいずれにおいても、トランザクションステータスの集合は同じである。

    チェックして、コメントでご意見をお聞かせください！

トランザクションステータスの集合
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - ステータス
     - 意味
   * - ``NOT_RECEIVED``
     - 要求されたピアはこのトランザクションを持っていない。
   * - ``ENOUGH_SIGNATURES_COLLECTED``
     - マルチシグネチャトランザクションは十分な署名を持ち、バリデーションされようとしている。
   * - ``MST_PENDING``
     - マルチシグネチャトランザクションはまだクォーラムに達するための署名が必要である。
   * - ``MST_EXPIRED``
     - マルチシグネチャトランザクションはもはや有効ではなく、削除されようとしている。
   * - ``STATELESS_VALIDATION_FAILED``
     - トランザクションが不正であるか署名が無効である。理由が返される。
   * - ``STATELESS_VALIDATION_SUCCESS``
     - トランザクションがステートレスバリデーションを通過した。送信直後に返される。
   * - ``STATEFUL_VALIDATION_FAILED``
     - コマンドがステート依存のルール（残高、パーミッションなど）に違反した。理由が返される。
   * - ``STATEFUL_VALIDATION_SUCCESS``
     - トランザクションがステートフルバリデーションを通過した。
   * - ``COMMITTED``
     - トランザクションは十分な票を得てブロックストアにあるブロックの一部である。
   * - ``REJECTED``
     - トランザクションは以前のコンセンサスラウンドのステートフルバリデーション中に拒否された。そのハッシュはリプレイ攻撃を防ぐために `ブロック <ブロック_>`__ ストアに格納される。

保留中のトランザクション
^^^^^^^^^^^^^^^^^^^^^^^^

その時点での署名数がトランザクション作成者アカウントの `クォーラム`_ より少ないトランザクションは保留中と見なされる。
保留中のトランザクションは、マルチシグネチャ機構がクォーラムに必要な署名数を集め次第、`ステートフルバリデーション`_ に提出される。

すでにクォーラムの署名を持つトランザクションも、`トランザクションのバッチ`_ の一部であり、十分に署名されていないトランザクションがある場合は保留中と見なされることがある。

トランザクションのバッチ
========================

トランザクションバッチは、順序を保ったまま複数のトランザクションを一度にIrohaへ送信できる機能である。

バッチ内の各トランザクションにはバッチメタ情報が含まれる。
バッチメタにはバッチタイプ識別子（アトミックまたは順序付き）とバッチ内のすべてのトランザクションの `縮小ハッシュ <トランザクションハッシュの縮小版_>`_ のリストが含まれる。
ハッシュの順序がトランザクションのシーケンスを定義する。

バッチには異なるアカウントが作成したトランザクションを含められる。
バッチ内の任意のトランザクションは単一の署名または `複数の署名 <マルチシグネチャトランザクション_>`__ を要求できる（トランザクション作成者のアカウントに設定されたクォーラムに依存する）。
バッチが `ステートレスバリデーション`_ を通過できるよう、バッチ内の少なくとも1つのトランザクションに少なくとも1つの署名が必要である。

バッチについての記事をコントリビューターズページの `Medium <https://medium.com/iroha-contributors/batches-in-iroha-117614cf1e88>`__ で読むことができる。

アトミックバッチ
----------------

アトミックバッチ内のすべてのトランザクションが `ステートフルバリデーション`_ を通過しなければ、バッチは台帳に適用されない。

アトミックバッチがステートフルバリデーションに失敗した場合、バッチ内のすべてのトランザクションがそれぞれ独自のステータス更新を受け取るので、失敗したトランザクションはステータスストリームから特定できる。

- 失敗したコマンドを含むトランザクションは、非空の ``err_or_cmd_name`` （失敗したコマンド名）、コマンド固有の ``error_code`` （コードの意味は `コマンドセクション <../develop/api/commands.html>`__ を参照）、および失敗したコマンドの位置（バッチ内ではなく **そのトランザクション内** の位置）を示す ``failed_cmd_index`` を持つ ``STATEFUL_VALIDATION_FAILED`` を受け取る。
- バッチ内の他のすべてのトランザクションは、空の ``err_or_cmd_name`` 、``error_code`` ``1`` 、および ``18446744073709551615`` （``SIZE_MAX`` 、「特定のコマンドなし」を意味する）の ``failed_cmd_index`` を持つ ``STATEFUL_VALIDATION_FAILED`` を受け取り、バッチがブロックにコミットされると ``REJECTED`` が続く。

したがって、バッチを壊したトランザクションを見つけるには、``err_or_cmd_name`` が空でないステータス更新を探せばよい。``failed_cmd_index`` はそのトランザクション内でどのコマンドが失敗したかを示す。

順序付きバッチ
--------------

順序付きバッチは台帳に適用されるトランザクションの順序のみを保持する。
バッチ内でステートフルバリデーションを通過できるトランザクションはすべて台帳に適用される。
1つのトランザクションのバリデーション失敗は、バッチ全体の失敗を直接意味しない。

マルチシグネチャトランザクション
================================

`クォーラム`_ が1より大きいトランザクションはマルチシグネチャ（mstとも呼ばれる）と見なされる。
`ステートフル有効性 <ステートフルバリデーション_>`__ を達成するには、作成者アカウントの `署名者 <署名者_>`__ による確認が必要である。
これらの参加者は同じトランザクションを自分の署名付きで送信する必要がある。

バリデーション
==============

バリデーションには2種類ある — ステートレスとステートフルである。

ステートレスバリデーション
--------------------------

`Torii <architecture.html#torii>`__ で実行される。
オブジェクトが署名を含めて正しい形式であるかをチェックする。

ステートフルバリデーション
--------------------------

`検証済み提案クリエーター <architecture.html#verified-proposal-creator>`__ で実行される。
`ワールドステートビュー <architecture.html#world-state-view>`__ に対してバリデーションを行う。
