============================
YAC コンセンサスアルゴリズム
============================

このセクションでは、Iroha がノード間で ledger の状態について
合意に達する方法 — YAC (Yet Another Consensus) メカニズムの
一部 — を説明します。

コンセンサスとは?
-----------------

Iroha は対等なノードのネットワークとして動作します。ユーザーが
トランザクションを送信すると、それは共通の順序付きリスト
（ブロック/提案）に含められ、すべてのノードによって適用される
必要があります。「コンセンサス」とは、ノードがこのリストの
内容と順序について合意するプロセスです。

Iroha は YAC のバリアントを使用します — ラウンドベースのプロトコルを
BFT 風のアプローチと組み合わせ、典型的なケースではファスト
パスの最適化を行うアルゴリズムです。

主要な概念
----------

**Ordering peers と syncing peers**
    genesis block または AddPeer コマンドで追加されたすべての
    ピアは、**ordering peer** （コンセンサスに参加）または
    **syncing peer** （読み取り専用）のいずれかです。syncing peer は
    投票せず、クォーラムにも数えられません — 確定済みブロックを
    直接受け取り、提案を作成しません。``Peer.syncing_peer`` フィー
    ルドがピアのクラスを決定します。glossary のエントリを参照。

**Rounds**
    コンセンサスは「ラウンド」で進行します。各ラウンドで ordering
    ピアはリーダー（proposer）を選出し、そのリーダーがトランザク
    ションを提案にまとめて他のピアに投票を求めます。提案がクォー
    ラムを得られない場合、新しいラウンドが始まります。

**Vote / Commit**
    各ピアは提案に対して「commit」または「reject」の投票を行い
    ます。commit 署名のクォーラムが集まると、提案はファイナライズ
    され、ブロックが ledger に書き込まれます。これがファイナリ
    ティです — ファイナライズされたブロック内のトランザクションは
    ロールバックされません。

**Byzantine-fault tolerance**
    YAC はビザンチン故障 — 任意または敵対的に振る舞うノード — への
    耐性を持つよう設計されています。理論上は N ≥ 3f + 1 のとき f 個
    までの故障ノードに耐えます。ただし標準の Iroha ビルドは YAC を
    **CFT** （crash-fault tolerant、単純多数決）モードで実行します
    — コンセンサスモデルのパラメータがコンパイル時定数だからです。
    詳細は後述。

CFT モード vs BFT モード
------------------------

YAC コードは両方のモデルをサポートします:

- ``YACMode::Cft`` — crash-fault tolerant: 誠実なノードの過半数が
  投票を待つだけでよい
- ``YACMode::Bft`` — byzantine-fault tolerant: 2f + 1 のクォーラムが
  必要

しかし値はコンパイル時定数 ``kCft`` によって設定されます —
デフォルトでは Iroha ビルドは CFT を使用します。BFT に切り替える
には ``kCft = false`` で再ビルドが必要です。つまり、典型的な
Iroha 1 デプロイは悪意あるノードではなくクラッシュに対して保護
されていることを意味します。

パフォーマンスと処理フロー
--------------------------

- ordering ピアは gRPC ポート ``internal_port`` （デフォルト
  ``10001`` ）経由で調整します。
- トランザクションはまず ``torii_port`` （クライアントインター
  フェース）を通り、キューに入り、その後提案に含まれます。
- 設定の ``vote_delay`` と ``proposal_creation_timeout`` パラメータ
  がラウンドのタイミングを制御します。:doc:`../configure/index`
  を参照。

Syncing nodes とコンセンサス
-----------------------------

syncing peer（:doc:`../deploy/syncing-node` 参照）はラウンドに
参加しません — ordering ピアから受け取った既にファイナライズさ
れたブロックを適用し、WSV を更新するだけです。これにより、
コンセンサスのレイテンシを増やさずに読み取りレプリカを持てます。
