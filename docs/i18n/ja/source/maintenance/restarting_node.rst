既存の WSV を持つ Iroha ノードの再起動
=====================================

以前は、ノードを更新する必要がある場合や何らかの理由でシャットダ
ウンした場合、すべてのブロックを再読み込みして一貫した `world
state view（WSV とも呼ばれる）
<../concepts_architecture/architecture.html#world-state-view>`__
を再作成するという選択肢しかありませんでした。ノードをより速く起
動するために、現在は簡単なチェック後に既存の WSV データベースを再
利用できます。そのために、トップブロックの ``hash`` と
blockstorage の ``height`` が WSV に含まれています。

.. warning::
	WSV が手動で編集されていないことを確認するのはノードの管理者
	の責任です – Iroha または `マイグレーションスクリプト
	<#changing-iroha-version-migration>`__ によってのみ編集される
	べきです。手動編集や信頼できるガイドラインに従わないマイグレ
	ションスクリプトの編集は、ネットワークの不整合につながる可能
	性があります。自己責任で行ってください（警告しました）。

いくつかのケースでは素晴らしいアイデアかもしれませんが、blockstor
age から WSV を復元する場合と比較して、WSV 再利用には特定の特性
があることに注意してください:

| :red:`信頼ポイント`
| **WSV の再利用:** blockstorage と WSV の両方に依存する必要が
  あります。
| **block storage からの WSV 復元:** genesis block のみを信頼し
  ます。


| :red:`整合性`
| **WSV の再利用:** blockstorage と WSV は一致している必要があ
  ります! Iroha はそれをチェックしません。
| **block storage からの WSV 復元:** Iroha は WSV を復元する間、
  すべてのブロックをチェックします。
	blockstorage のエラーはすべて見つかります（もちろん genesis
	block を除く）。
	WSV が blockstorage と一致することが保証されます。

| :red:`時間`
| **WSV の再利用:** Iroha はほぼすぐにネットワークで動作する準
  備ができます。
| **block storage からの WSV 復元:** blockstorage が大きいほど、
  復元と動作開始に時間がかかります。

.. note:: シャットダウンしたローカル台帳があるべきより多くのブロ
ックを持ち、正しい WSV がその中にある場合 — 問題ありません。Iroha
は正しいブロックの WSV を取得します。
	ブロックがあるべきより少ない場合 — WSV 再利用オプションは機
	能しません。
	ブロックから復元してください。


WSV の破棄
^^^^^^^^^^

デフォルトでは Iroha は起動時に WSV 状態を再利用するため、
`--reuse_state` フラグはもう必要ありません。ただし後方互換性のた
めに残されています。WSV 状態を破棄したい場合は、Iroha を
``--drop_state`` フラグで起動してください。このフラグを指定する
と、Iroha は状態データベースをリセットして上書きします。

状態データベースのスキーマバージョン
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

既存の WSV を再利用する場合、Iroha はスキーマバージョンの互換性
チェックを実行します。スキーマが使用中の Iroha と互換性がない場合
、データベースを起動したり変更したりしません。

スキーマがバージョン v1.1.1 以下の Iroha で作成された場合、おそら
くバージョン情報が含まれていません。この場合は手動で追加する必要
があります。この目的には私たちのスクリプトの使用をお勧めします。
`こちら
<https://github.com/hyperledger-iroha-state-migration-tool/blob/master/state_migration.py>`__
にあります。スキーマバージョンを強制的に（つまり、いかなる
`マイグレーションプロセス
<#changing-iroha-version-migration>`__ なしに）設定するには、
スクリプトを `--force_schema_version` フラグで起動し、スキーマの
作成に使用された Iroha バイナリのバージョンを渡してください。

.. warning::
  スキーマバージョン番号を強制的に書き込む前に、スキーマを作成し
  た irohad のバージョンを再確認してください。
  スキーマ番号を強制する際にはチェックが行われないため、将来
  （次のマイグレーション時に）状態データベースを壊すのは容易で
  す。

Iroha バージョンの変更。マイグレーション。
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
WSV を保持したまま Iroha バージョンを変更したい場合は、マイグレー
ションを実行することをお勧めします。スキーマが互換性がない場合 Iroha
は起動を拒否するため不要かもしれませんが、一般的なルールとして、私
たちは各バージョンでスキーマを改善しており、マイグレーションはより
良いパフォーマンスのための良いアイデアかもしれません。マイグレー
ション前に標準的な `PostgreSQL ガイドライン
<https://www.postgresql.org/docs/current/backup.html>`__ を使用し
てデータベースのバックアップを実行することをお勧めします。

マイグレーションを実行するには、私たちの `スクリプト
<https://github.com/hyperledger-iroha-state-migration-tool/blob/master/state_migration.py>`__
を使用してください。

データベースからスキーマ情報を読み込み、マイグレーションステップ
と照合します（デフォルトでは、マイグレーションシナリオはスクリプ
トと同じフォルダーの ``migration_data`` ディレクトリで定義されてい
ます）。次に、データベースを目的のバージョンに移行するすべてのマイ
グレーションパスを見つけ、1 つを選択するよう求めます。

.. seealso::
	`こちら
	<https://github.com/hyperledger-iroha-state-migration-tool/blob/master/README.md>`__
	には、さまざまなマイグレーションケースと、マイグレーションを実
	行するために確認できる例の詳細があります

WSV 同期モード。
^^^^^^^^^^^^^^^^

WSV 同期モードには ``--wait_for_new_blocks`` オプションを指定しま
す。Iroha は blockstore から WSV を復元し、外部から新しいブロックが
追加されるのを待ちます。このモードでは Iroha はネットワーク操作を
実行しません。
