コマンド
========

コマンドは、システム内のエンティティ（アセット、アカウント）に対してアクションを実行することで、ワールドステートビューと呼ばれる状態を変更します。
すべてのコマンドは、アクションを実行するためにトランザクションに含める必要があります。

エラーコード
------------

すべてのコマンドは失敗し、トランザクションステータスで報告される数値の ``error_code`` を持つ可能性があります。
コード ``0`` 、 ``1`` 、 ``2`` はすべてのコマンドで同じ意味を持ちます
（ ``0`` = 成功、 ``1`` = 内部エラー、 ``2`` = 権限なし）。
コード ``>= 3`` はコマンド固有です。

正式な定義は ``shared_model/interfaces/command_error_codes.hpp`` にあり、
これはコマンドエグゼキューター（Postgres および RocksDB バックエンド）と
クライアントライブラリによって共有されています。以下の表はクイックリファレンス用に
コマンドごとのコードを要約したものです。完全なヘッダーはその後に再掲しています。
表とヘッダーが食い違う場合は、 **ヘッダーが正** です。ヘッダーこそが
エグゼキューターが実際に出力するものです。

``AddSyncPeer``/``RemoveSyncPeer`` のエラーネームスペースは同期ピア機能のために
ヘッダーに存在しますが、それらを出力するクライアント向けコマンドはまだありません。

コード ``1007`` と ``1008`` は RocksDB コマンドエグゼキューター（テストバックエンド）のみが
出力します。 ``1007`` = 権限がすでに設定済み（ ``grant_permission`` ）、
``1008`` = 空の公開鍵（ ``remove_peer`` ）。
Postgres バックエンドには対応するコードはありません。

資産量の追加
------------------

目的
^^^^^^^

資産量追加コマンドの目的は、トランザクション作成者のアカウント上のアセットの数量を増やすことです。
使用例としては、コモディティ（例：金銭、金など）への請求権として機能できる、システム内の
ミュータブルアセットの数を増やすことが挙げられます。

スキーマ
^^^^^^^^

.. code-block:: proto

    message AddAssetQuantity {
        string asset_id = 1;
        string amount = 2;
        optional string description = 3;
    }

.. note::
    既知の問題により、無効な精度値を渡しても例外は発生しませんのでご注意ください。
    有効な範囲は: 0 <= precision <= 255


構造
^^^^^^^^^

.. csv-table::
    :header: "フィールド", "説明", "制約", "例"
    :widths: 15, 30, 20, 15

    "アセット ID", "アセットの ID", "<asset_name>#<domain_id>", "usd#morgan"
    "数量", "追加するアセットの正の数量", "> 0", "200.02"
    "説明", "トランザクションの説明", "説明の最大長（ジェネシスブロックで設定、デフォルトは 100*1024）", "Mint assets"

検証
^^^^^^^^^^

1. アセットとアカウントが存在すること
2. 追加する数量の精度がアセットの精度と一致すること
3. トランザクションの作成者がアセット発行権限を持つロールを持っていること

    "3", "No such asset", "そのような名前または精度のアセットが見つからない", "アセット ID と精度が正しいことを確認する"
    "4", "Summation overflow", "結果のアセット数量がシステムがサポートできる範囲を超えている", "結果の数量が 2^256 / 10^asset_precision 未満であることを確認する"

`Add Peer コマンドについて詳しく知る <../../maintenance/add_peer.html>`_ こともできます。

署名者の追加
-------------

目的
^^^^^^^

署名者追加コマンドの目的は、アカウントに識別子を追加することです。
そのような識別子は、別のデバイスまたは別のユーザーの公開鍵です。

スキーマ
^^^^^^^^

.. code-block:: proto

    message AddSignatory {
        string account_id = 1;
        bytes public_key = 2;
    }

構造
^^^^^^^^^

.. csv-table::

^^^^^^^^^^

2 つのケースがあります。

ロールの追加
------------

目的
^^^^^^^

ロール追加コマンドの目的は、アカウントをシステム内の作成済みロールに昇格させることです。ここでロールとは、アカウントがアクション（コマンドまたはクエリ）を実行するために必要な権限の集合です。

スキーマ
^^^^^^^^

.. code-block:: proto

    message AppendRole {
       string account_id = 1;
       string role_name = 2;
    }

構造
^^^^^^^^^

.. csv-table::
    :header: "フィールド", "説明", "制約", "例"
    :widths: 15, 30, 20, 15

    "アカウント ID", "ロールを追加するアカウントの ID", "既に存在すること", "makoto@soramitsu"
    "ロール名", "作成済みロールの名前", "既に存在すること", "MoneyCreator"

検証
^^^^^^^^^^

1. ロールがシステム内に存在すること
2. トランザクション作成者がロールを追加する権限（CanAppendRole）を持っていること
3. ロールを追加するアカウントが、自身のロールに持つ権限の集合が、追加されるロールの権限の上位集合であること（言い換えれば、誰もトランザクション作成者より強力なロールを追加することはできない）

エンジンの呼び出し
------------------

目的
^^^^^^^

エンジン呼び出しコマンドの目的は、Iroha EVM に新しいコントラクトをデプロイするか、既存のスマートコントラクトのメソッドを呼び出すことです。
このコマンドを含むトランザクションがブロックに受け入れられ、そのブロックがコミットされれば、スマートコントラクトの実行は台帳の状態を変更する可能性があります。

スキーマ
^^^^^^^^

.. code-block:: proto

    message CallEngine {
        string caller = 1;
        oneof opt_callee {
            string callee = 2;  // hex string
        }
        string input = 3;   // hex string
    }

構造
^^^^^^^^^

.. csv-table::
    :header: "フィールド", "説明", "制約", "例"

    "Caller", "このコマンドが代理として実行されるアカウントの Iroha アカウント ID", "<account_name>@<domain_id>", "test@mydomain"
    "Callee", "デプロイされたスマートコントラクトの EVM アドレス", "16 進数表記の 20 バイト文字列", "7C370993FD90AF204FD582004E2E54E6A94F2651"
    "Input", "新規デプロイするコントラクトのバイトコード、または `その引数セット <https://solidity.readthedocs.io/en/v0.6.5/abi-spec.html>`_ に続くコントラクトメソッドセレクタの ABI エンコード文字列", "16 進数文字列", "40c10f19000000000000000000000000969453762b0c739dd285b31635efa00e24c2562800000000000000000000000000000000000000000000000000000000000004d2"

検証
^^^^^^^^^^

1. Caller が有効な Iroha アカウント ID であること
2. トランザクション作成者が can_call_engine または can_call_engine_on_my_behalf 権限を持つロールを持っていること

アカウント詳細の比較・設定
------------------------------

目的
^^^^

アカウント詳細の比較・設定コマンドの目的は、渡された値が古い値と一致する場合に、指定されたアカウントにキーと値の情報を設定することです。

スキーマ
^^^^^^^^

.. code-block:: proto

    message CompareAndSetAccountDetail{
        string account_id = 1;
        string key = 2;
        string value = 3;
        oneof opt_old_value {
            string old_value = 4;
        }
        bool check_empty = 5;
    }

.. note::
    old_value フィールドがオプションであることに注意してください。
    これは、キーと値のペアが存在しない可能性があるためです。

構造
^^^^

    :widths: 15, 30, 20, 15

    "アカウント ID", "キーと値の情報が設定されるアカウントの ID。キーと値のペアが存在しない場合は作成されます", "既存のアカウント", "artyom@soramitsu"
    "キー", "設定される情報のキー", "`[A-Za-z0-9_]{1,64}`", "Name"
    "値", "対応するキーの新しい値", "値の長さ ≤ 4096", "Artyom"
    "古い値", "対応するキーの現在の値", "値の長さ ≤ 4096", "Artem"
    "check_empty", "true の場合、コマンドの空の old_value が WSV に存在しない値と一致する必要があります。false の場合、コマンドの任意の old_value が WSV に存在しないことと一致します（レガシー）", "bool", "true"

検証
^^^^

3 つのケース:

    ケース 1. トランザクションの作成者が自分のアカウントにアカウント詳細を設定したい場合で、作成者が GetMyAccountDetail / GetAllAccountsDetail / GetDomainAccountDetail 権限を持っている場合

    ケース 2. トランザクションの作成者が別のアカウントにアカウント詳細を設定したい場合で、作成者が SetAccountDetail 権限と GetAllAccountsDetail / GetDomainAccountDetail 権限を持っている場合

    ケース 3. SetAccountDetail 権限がトランザクションの作成者に付与されており、作成者が GetAllAccountsDetail / GetDomainAccountDetail 権限を持っている場合
