まずは、貢献のために時間を割いてくださり、ありがとうございます！

以下は、Iroha への貢献に関する短いガイドラインです。

貢献の仕方
----------

ドキュメントの翻訳
~~~~~~~~~~~~~~~~~~

このドキュメントの翻訳版は、英語版と同じく ``/<language>/`` の下に
ホスティングされています。現在利用可能なもの:

* **Türkçe** — `Türkçe dokümantasyon <../tr/>`_ (アーカイブされた
  :strikelink:`hyperledger-iroha/iroha-docs-l10n
  <https://github.com/hyperledger-iroha/iroha-docs-l10n>` リポジトリから
  翻訳。翻訳は Iroha 1.2 時代のドキュメントをカバーしており、
  英語版に遅れている可能性があります)

ポーランド語を含む他の言語も計画されています。翻訳への貢献を希望する
場合は、`Discord <https://discord.com/channels/905194001349627914/905205848547155968>`_ で
お気軽にご連絡ください。

バグの報告
~~~~~~~~~~

*バグ* とは、Iroha におけるエラー、設計上の欠陥、失敗、または不具合で、
誤った結果や予期しない結果を生み出したり、意図しない動作をしたりする
ものを指します。

バグは `GitHub issue <https://github.com/hyperledger-iroha/iroha/issues>`_ として
管理されています。

バグを報告するには、`新しい issue を作成
<https://github.com/hyperledger-iroha/iroha/issues/new>`_ し、issue テンプレートに
問題の概要、再現手順、関連するログなどの詳細を記載してください。また、
環境の詳細(OS、デバイス仕様、Iroha のバージョンなど)もご提供ください。

脆弱性の報告
~~~~~~~~~~~~

セキュリティ上の問題を未然に防ぐよう努めていますが、決して起こらない
と仮定しているわけではありません。

公開する前に、ベンダー(Hyperledger 組織)へ責任を持って非公開でセキュリティ
上の問題を開示するのが標準的な慣行であり、修正を準備し、脆弱性による
被害を最小限に抑えることができます。

最初のメジャーリリース(1.0)の前は、すべての脆弱性はバグとして扱われ
ますので、上記の方法で自由に報告してください。最初のメジャーリリース
以降は、脆弱性の報告と報酬の受け取りのために `こちらのバグバウンティ
プログラム <https://hackerone.com/hyperledger>`__ をご利用ください。

いずれの場合でも、ご自身の発見が脆弱性かバグかどうか議論したい場合は、
Discord のプライベートメッセージまたは電子メール(CONTRIBUTORS.md
ファイルを参照)で、既存のメンテナーのいずれかにお気軽にご連絡ください。

改善提案
~~~~~~~~

*改善* とは、**既存の** コードや設計をより高速、より安定、移植性が高く、
セキュアに、あるいはその他の点でより良くするコードまたはアイデアを
指します。

改善は `GitHub issue <https://github.com/hyperledger-iroha/iroha/issues>`_ として
管理されています。

新しい改善を提案するには、`新しい issue を作成
<https://github.com/hyperledger-iroha/iroha/issues/new>`_ し、アイデアを説明して
ください:何を改善し、なぜ価値があるのか。コードの提案がある場合は、
ぜひ含めてください。

質問
~~~~

*質問* とは、典型的にはバグでも機能リクエストでも改善でもない、あらゆる
議論を指します。「X をどうやってやるの?」のような質問がある場合は、
このセクションがあなたのためのものです。

質問は `お気に入りのメッセンジャー <コミュニティがアクティブな場所>`__ に
投稿してください。コミュニティのメンバーが助けてくれます。あなた自身も
他の人を助けることができます!

最初のコード貢献
~~~~~~~~~~~~~~~~

`C++スタイルガイド <C++スタイルガイド>`__ を読み、
`GitHub ボード <https://github.com/hyperledger-iroha/iroha/projects/1>`_ または
`good-first-issue ラベル <https://github.com/hyperledger-iroha/iroha/issues?q=is%3Aissue+is%3Aopen+label%3Agood-first-issue>`_
付きの issue を確認することから始めてください。そのタスクに取り組んで
いることを何らかの形で示してください:メンテナーチーム、コミュニティに
連絡するか、単にその issue を自分にアサインしてください。

プルリクエスト
~~~~~~~~~~~~~~

-  `必須のテンプレート <https://github.com/hyperledger-iroha/iroha/blob/iroha1-main/.github/PULL_REQUEST_TEMPLATE.md>`_
   を記入する

-  すべてのファイルを改行で終える

-  新しいコードには**テストを書く**。新しいコードのテストカバレッジは
   少なくとも 70% でなければならない

-  すべてのプルリクエストはレビューされ、**メンテナーチームから少なく
   とも 2 件の承認を得る** 必要がある。現在のメンテナーは
   `MAINTAINERS.md <https://github.com/hyperledger-iroha/iroha/blob/iroha1-main/MAINTAINERS.md>`_
   ファイルを確認すること

-  作業が終わったら、すべての CI チェックがパスしていることを確認し
   てください。その後、プルリクエストを**スカッシュしてマージ** して
   ください

-  `C++スタイルガイド <C++スタイルガイド>`__ に従う

-  `Gitスタイルガイド <Gitスタイルガイド>`__ に従う

-  `ドキュメントスタイルガイド <ドキュメントスタイルガイド>`__ に基づいて
   **新しいコードを文書化** する

-  **フォークからの PR** を扱う場合は `この
   マニュアル <https://help.github.com/articles/checking-out-pull-requests-locally>`__ を
   確認する

スタイルガイド
--------------

Gitスタイルガイド
~~~~~~~~~~~~~~~~~

-  `DCO <https://github.com/apps/dco>`_ で**すべてのコミットに
   サインオフする**: ``Signed-off-by: $NAME <$EMAIL>``。
   ``git commit -s`` を使って自動的に行うことができます
-  **現在形を使う** ("Add feature" であって "Added feature" ではない)。
-  **命令形を使う** ("Deploy docker to..." であって "Deploys docker
   to..." ではない)。
-  意味のあるコミットメッセージを書く。
-  コミットメッセージの1行目を50文字以内に制限する
-  コミットメッセージの1行目には行った作業の要約を含め、2行目は空行に
   し、3行目以降にはコミットの変更点のリストを含めることができる
-  宛先ブランチにマージする際は:**スカッシュしてマージ** を使用する

C++スタイルガイド
~~~~~~~~~~~~~~~~~

-  clang-format
   `設定ファイル <https://github.com/hyperledger-iroha/iroha/blob/iroha1-main/.clang-format>`_
   を使用する。インターネット上にガイドが利用可能です(例: `Kratos
   wiki <https://github.com/KratosMultiphysics/Kratos/wiki/How-to-configure-clang%E2%80%90format>`_)
-  `CppCoreGuidelines <http://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines>`_
   と `Cpp Best
   Practices <https://lefticus.gitbooks.io/cpp-best-practices>`_ に従う。
-  `プラットフォーム依存 <https://stackoverflow.com/questions/1558194/learning-and-cross-platform-development-c>`_
   のコードを避ける。
-  `C++23 <https://en.wikipedia.org/wiki/C%2B%2B23>`_ を使用する。
-  クラス名とメソッドには `camelCase <https://en.wikipedia.org/wiki/Camel_case>`_ を、
   変数には `snake\_case <https://en.wikipedia.org/wiki/Snake_case>`_ を使用する。

ドキュメントスタイルガイド
~~~~~~~~~~~~~~~~~~~~~~~~~~

-  `Doxygen <http://www.doxygen.nl/>`_ を使用する。
-  すべてのパブリック API を文書化する:メソッド、関数、メンバー、
   テンプレート、クラス...
